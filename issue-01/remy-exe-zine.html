01

LEVEL 1 START

I needed a site to document all my AI projects. But I wasn't going to build a run-of-the-mill site. I needed something that oozes personality and my taste, where I could provide creative direction in collaboration with AI to create it.

This is the proof I can not only build functional stuff, but also awesome-looking design.

A site without a point of view is a CV in different fonts.

The framing landed quickly: a zine. Not a portfolio, not a blog, not a Notion page. A digital magazine, with me as editor, writer, designer, and developer. Issues come out at the cadence the work ships. Each chapter documents one project with the same template (LEVEL 1 START / BOSS FIGHT / INVENTORY / XP GAINED) and a different signature color. The whole site is one of the projects. This chapter is the one about how it got built.

02

BOSS FIGHT

Most websites get built around a content model. You decide what kinds of things go on the site (posts, projects, products), then design a layout that makes those things look right.

This one went the other way. The design language landed first. I wanted the site to feel like a videogame-flavored digital magazine. Pixel fonts where they could carry weight, a serif for body copy, a monospace terminal font for system messages. Signature colors per chapter, like a magazine using a different ink for each section. A pixel-art mascot, because of course.

▸ ASTRO + TAILWIND

The stack picked itself once the framing was clear.

Astro because the site is content-driven, not app-driven. Each chapter is a markdown document with components inline. Static output, fast loads, no client-side framework runtime to ship. The site is a magazine, not a SPA. Astro is the closest thing to "publishing platform that respects HTML."

Tailwind because the design system needed tokens (signature colors, type scale, spacing rhythm) and Tailwind is the cleanest way to lock those tokens at the config level and reuse them across components without writing CSS files for every variant. The static version of the site was a 60KB single HTML file with a 1,000-line <style> block. Migrating to Tailwind let the same design tokens live in one config file and propagate everywhere.

Other things considered: Next.js (overkill, app-shaped not content-shaped), plain HTML/CSS (the static version, fine until I needed to scale to multiple chapters), Eleventy (good fit, but Astro's component model felt closer to where I wanted the chapter templates to live).

▸ GOTCHA

Press Start 2P, the pixel-art font that does most of the loud typography on the site, doesn't have accented character glyphs. When the credits roll spelled my name as RÉMY in the pixel font, the É rendered as a smaller lowercase é from the browser's fallback font, sitting between an uppercase R and MY. It looked like the accent had been dropped in mid-render. The fix was to drop the accent in pixel-font contexts (the credits roll uses REMY) and keep it in body-text contexts where Fraunces handles diacritics fine. Real takeaway: pixel fonts encode the language they're designed for, usually English-only ASCII. Worth checking before falling in love with one.

▸ GOTCHA

The first four chapters were built one at a time, each with its full design system embedded in a <style> block at the top of the HTML file. By chapter five, the same 800 lines of CSS had been duplicated five times. Changing the cyan signature color now meant editing five files. Adding a new component meant five edits. The mistake wasn't writing it that way once. The mistake was not stopping at chapter two and pulling the shared rules into a single shared/style.css. The fix was a single extraction pass after all five chapters were homologated, when the design system was finally locked. Lesson: the cost of duplication grows linearly. The cost of extraction stays roughly flat. Extract early, even when "early" feels premature.

▸ CONTENT AND DESIGN SEPARATED

Every chapter's design lives in one shared stylesheet (shared/style.css). Every chapter's content lives in its own HTML file. Changing a color is a one-line edit in the stylesheet and every chapter, current and future, picks it up. Authoring a new chapter is a content task, not a styling task.

This separation is the architecture. The marginal cost of adding a new chapter is the cost of writing its content. There's no system-rebuilding tax.

▸ EDITORIAL RULES
  • No em-dashes. Anywhere in body copy. Periods, commas, parentheses, semicolons instead. Em-dashes are a known AI-writing tell.
  • First-person singular. Everything written from "I." No "we," no "the team."
  • Tab subtitles are fixed. the why / the fix / the stack / learnings. Same in every chapter.
  • Industry-then-project structure in LEVEL 1 START when applicable. Industry framing first, then ▸ AT [PROJECT] divider, then project-specific framing.
  • Status tags. LIVE for everything currently shipping. WIP for genuinely in-progress chapters that should be readable but flagged.

04

XP GAINED

▸ AI POWER-UPS

building with ai
  • MOCKUPS BEFORE PROMPTS

    When building visual UI with AI, sketching the screen as text-only first (just labels and arrows on a page, no pixels) gets dramatically better results than describing it in prose. The AI can see the information architecture before it has to invent layout. Skip the IA step and the AI fills the gap with whatever generic SaaS pattern is statistically average.

  • DESIGN LANGUAGE AS A BRIEF

    Loading the AI with the design tokens, font choices, signature colors, and editorial rules upfront means every component request lands in the same visual register. Without that, components drift toward whatever framework the AI saw most often. Front-load the brief, save hours of back-and-forth corrections.

  • SHOW, DON'T TELL

    Pasting an existing component as a reference produces faster, more accurate variants than describing one from scratch. The AI is much better at "make this but for that case" than at "build me a card with these properties." Use the components you already have as the language.

  • AI WON'T VOLUNTEER ARCHITECTURE

    When you're shipping fast with AI, it ships fast with you. It will happily duplicate a 1,000-line stylesheet across five files if you ask it to build five files. It will not interrupt the flow to say "this is going to be painful in three months." That's the human's job. The lesson: at every milestone (second chapter, third feature, second similar component), pause and explicitly ask the AI to flag any structural decisions you're about to lock in by default. Otherwise you'll keep shipping and accumulate debt that only becomes visible when scale forces a refactor.

▸ PRODUCT SPECIAL MOVES

product thinking
  • THE WRAPPER IS A PRODUCT

    Most PMs treat their portfolio as a packaging exercise: pick a template, drop in case studies, ship. Treating the wrapper as one of the projects forces the same product thinking on it (audience, frame, point of view) and that thinking is what makes the difference between a fungible site and a memorable one.

  • A SYSTEM IS CHEAPER THAN A PAGE

    Building chapter 01 took longer than chapters 02-05 combined, because the first chapter had to invent the template every other chapter would inherit. The right unit of work was always the system, not the page. Same lesson that applies to building products: the second feature is cheap if the first one was built right.

▸ DEV SECRETS DISCOVERED

development learnings
  • SEPARATE FORMAT FROM CONTENT

    Tailwind utility classes locked the design tokens at the config level so individual components don't carry their own styling state. Migrating from a 1,000-line <style> block to Tailwind config wasn't refactoring. It was finally putting the design system in its own layer, where editing tokens means everything downstream updates without touching component markup.

  • MARKDOWN IS THE RIGHT BACKEND

    Each chapter as a markdown file with components inline is the right separation. The writing lives in plain text. The styling lives in components. Authoring a new chapter doesn't require touching CSS, and refactoring a component doesn't require touching prose. Every CMS gets re-invented to recover this property.

  • CLAUDE CODE FOR REPETITION, ME FOR DECISIONS

    Once the design system was locked, building a new chapter was a Claude Code task: feed the existing template, paste the chapter's content, run. The hours that would have gone into typing went into the decisions that mattered: which fonts, which colors, which copy, which gotcha to document. Right division of labor.

▸ SIDE QUESTS

future iterations
  • ISSUE 02 AS THE TEST

    The real test of whether the system works is shipping issue 02. If new chapters in issue 02 take meaningfully less time than chapters in issue 01, the system earned itself. If not, the design language is doing less work than it looks like.

  • DARK MODE / LIGHT MODE SWITCHER

    Currently dark-mode-only. A light-mode variant would test how robust the design tokens really are. Most design systems break under inversion because too many components hardcode their colors instead of referencing tokens. Worth shipping as a forcing function on cleanup.

  • A REAL MASCOT NAME

    Still no name for the critter. Submission rules are out (LinkedIn, under 8 chars, pronounceable). When the right one shows up, ship it.

  • INTERACTIVE COMPONENT DOCS

    This INVENTORY section is a static documentation page. A version where each component is editable in-place, with the prop interface visible, would make handoff to a real dev team trivial. Storybook-shaped, but living inside the zine.
