<Panel id="p-origin" num="01" title="LEVEL 1 START" open>

Data extraction for reporting, visualization, and decision-making is one of the most underrated time sinks in product work. When the data lives in an external platform, there is usually a visualization solution built into it. But getting to that visualization requires someone to build the right query, configure the right view, and maintain it when requirements change.

Regarding data, most of my work is in the context of A/B testing. Key data for that lives in *CleverTap*, an engagement and analytics platform that tracks user behavior across experiments, funnels, and events. It has a solid dashboard. But that dashboard requires someone to configure the right views.

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE SCENARIO</span>
  <div class="divider-line"></div>
</div>

A/B testing compounds this pain fast. Four active experiments running at once, each with up to five variants, across two countries and two operating systems. To analyze results properly, every combination needs to be queried, updated daily, stacked by date. That is not something a dashboard handles. It is something that turns into a late night without warning.

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE UNLOCK</span>
  <div class="divider-line"></div>
</div>

CleverTap has an API. Every major analytics platform does. And *Google Apps Script* is a scripting environment built directly into Google Sheets that can call any API you have credentials for. No server, no deploy, no ticket. Write a script, set a trigger, get fresh data in a spreadsheet on a schedule.

<Panel id="p-fix" num="02" title="BOSS FIGHT">

The goal was straightforward: pull daily event counts for a 12-step funnel, broken down by experiment variant, country, and operating system, within a defined time frame, updated daily. CleverTap had all of it. The task was writing a script that would actually hold up as a daily pipeline.

It did not go in a straight line. Each wall hit revealed something specific about how the API actually worked versus what the dashboard suggested. This is that story.

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE ASYNC WALL</span>
  <div class="divider-line"></div>
</div>

The first call to CleverTap's Counts API came back with a <code>partial</code> status and a job ID instead of data. The platform queues analytics queries server-side and processes them asynchronously. You take the <code>req_id</code>, poll a separate GET endpoint every 30 seconds, and wait for <code>success</code>. That two-step cycle is the heartbeat of every interaction with this API.

<div class="walk-code">{`POST /counts/events.json → { "req_id": "164266", "status": "partial" } → GET ?req_id=164266 → { "count": 46097, "status": "success" }`}</div>

<Gotcha tag="⚠ GOTCHA · POLLING TOO FAST">
Hitting the poll endpoint before the query finishes just returns another <code>partial</code>. The API needs time to process. The 30-second wait is not a workaround: it is the correct usage pattern.
</Gotcha>

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE WRONG SCOPE</span>
  <div class="divider-line"></div>
</div>

The first script Claude produced pulled raw event records, one row per event occurrence, paginated across thousands of results. That was not what was needed. The actual requirement was simpler: total count per event per day. One number. Not every individual event. Fixing the scope meant switching from the export API to the Counts API entirely, which also eliminated the pagination problem that was crashing the script anyway.

<Gotcha tag="⚠ GOTCHA · UNDER-SPECIFIED PROMPT">
The first version of the prompt asked for "the data." That is too vague. "One count per event per day per dimension combination" is the correct spec. The AI generates exactly what you ask for. If the output is wrong, the spec is wrong.
</Gotcha>

<Win tag="✓ WIN · COUNTS OVER RECORDS">
One number per day per dimension is all Looker Studio needs to build a funnel. Switching to the Counts API simplified the architecture and fixed two problems at once.
</Win>

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE FIELD NAME WALL</span>
  <div class="divider-line"></div>
</div>

Filtering by OS looked simple. The CleverTap dashboard shows "OS = Android" as a user property filter. The API does not accept that syntax. The field lives under a key called <code>technographics</code> inside <code>common_profile_properties</code>. Country filtering is different still: it uses <code>geo_fields</code>, formatted as nested arrays with full country names, not codes.

<div class="walk-code">{`common_profile_properties: { technographics: [{ name: "OS", value: "Android" }], geo_fields: [["United States"]] }`}</div>

<Gotcha tag="⚠ GOTCHA · DASHBOARD LABELS VS API FIELDS">
The dashboard showed <code>Country = US</code>. The API required <code>geo_fields: [["United States"]]</code>. Every platform has this gap. Reading the documentation is not optional. Guessing from UI labels produces code that compiles and returns nothing.
</Gotcha>

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE EXPERIMENT BRIDGE</span>
  <div class="divider-line"></div>
</div>

The hardest conceptual piece: CleverTap does not tag funnel events with which experiment a user belongs to. The bridge is a separate event called <code>ab_test_audience</code> that fires when a user is enrolled in an experiment. To count funnel events per variant, you filter to users who also fired that enrollment event with the correct variant ID, expressed as a nested query inside the main payload.

<div class="walk-code">{`advanced_query: { did_all: [{ event_name: "ab_test_audience", event_properties: [{ name: "Variant", operator: "contains", value: "59e747ae..." }] }] }`}</div>

<Win tag="✓ WIN · FILTER CONFIRMED">
Tested on a single day: Baseline returned 1, Variant A returned 4. Different numbers, both non-zero. The segmentation was real and working.
</Win>

  <span class="divider-label">▸ THE SPEED WALL</span>
  <div class="divider-line"></div>
</div>

The first working version ran all queries sequentially: fire one call, wait 30 seconds for the poll, write the result, fire the next. With over 2,600 total queries across all experiments, variants, funnel steps, and days, that approach translated to roughly 22 hours of pure wait time.

<div class="fix-grid">
  <div class="fix-card before">
    <span class="fix-tag">✗ BEFORE</span>
    Call step 1 → wait 30s → write → call step 2 → wait 30s...
    <br/><br/>
    12 steps × 30s = <strong>6 minutes per variant</strong>
  </div>
  <div class="fix-card after">
    <span class="fix-tag">✓ AFTER</span>
    Fire all 12 steps at once → wait 30s once → poll all 12 → write all 12
    <br/><br/>
    12 steps + 1 wait = <strong>~40 seconds per variant</strong>
  </div>
</div>

<Win tag="✓ WIN · 10X FASTER">
Batching all 12 funnel steps per variant, waiting once, and polling all results together made the script roughly 10 times faster. The historical load finished across a few overnight runs instead of days.
</Win>

<div class="section-divider">
  <div class="divider-line"></div>
  <span class="divider-label">▸ THE MASTER PROMPT</span>
  <div class="divider-line"></div>
</div>

Somewhere in the middle of all of this, the pattern became visible. Every wall came down to the same set of questions: how does this API handle async responses, what are the actual field names for each filter dimension, how should the output be structured so it works in Looker Studio without rework, and how does the script stay alive across execution limits. Answer those four questions upfront and the script writes itself.

That became a prompt. Not a general "help me write an Apps Script" prompt. A structured discovery process specific to pulling CleverTap A/B test data that front-loads the spec before generating any code. Think of it like a waiter taking an order: they don't hand you the kitchen's full ingredient list. They ask the right questions in the right order to get you what you actually want.

<div class="prompt-box">
  <span class="prompt-box-label">◈ PROMPT SPEC · CLEVERTAP A/B TEST PIPELINE</span>
  <div class="prompt-io">
    <div class="prompt-io-card">
      <span class="prompt-io-label input">INPUT · WHAT YOU BRING</span>
      <ul class="prompt-io-list">
        <li>CleverTap credentials and region</li>
        <li>Experiment name and variant identifiers</li>
        <li>Funnel events to measure, in order</li>
        <li>Segmentation dimensions: country, OS</li>
        <li>Date range and refresh cadence needed</li>
      </ul>
    </div>
    <div class="prompt-io-card">
      <span class="prompt-io-label output">OUTPUT · WHAT YOU GET</span>
      <ul class="prompt-io-list">
        <li>Working script with auth and retry built in</li>
        <li>Correct CQL field names for each filter</li>
        <li>Long-format schema ready for Looker Studio</li>
        <li>Checkpoint system for large historical loads</li>
        <li>Daily trigger configuration included</li>
      </ul>
    </div>
  </div>
  <div class="prompt-how">
    <span class="prompt-how-label">HOW IT WORKS</span>
    <p>The prompt opens with discovery questions before any code is written. It establishes whether the API response is synchronous or async, what the variant identifiers look like in the actual data, how the experiment filter connects to the funnel events via <code>ab_test_audience</code>, and what the output schema needs to be for Looker Studio. These are the variables that change between experiments, and the questions that produce zeros when skipped.</p>
    <p>The second phase locks the data structure: long format, one row per dimension combination, with dimensions as columns and count as the metric. Once those decisions are made explicitly, the code is just execution of a spec that already exists.</p>
  </div>
</div>

  <ul class="xp-learnings">
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">READ THE DOCS BEFORE GENERATING CODE</div>
        <p class="xp-learning-desc">AI writes confident code against APIs it partially knows. The CleverTap field names (<code>technographics</code>, <code>geo_fields</code>, <code>advanced_query</code>) are not guessable from general knowledge. They require reading the actual documentation. When that step was skipped, the output was plausible-looking code that returned zero results. The fix: prompt Claude to fetch and read the docs first, then write the code against what they actually say.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">TEST ONE CALL BEFORE LOOPING</div>
        <p class="xp-learning-desc">Every working script in this chapter started as a single hardcoded test: one day, one variant, one event. Confirm the API responds correctly, confirm the filter works, confirm the number matches the source dashboard, then generalize into a loop. Looping first hides which variable is broken and turns a short debug into a long guessing session.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">THE SPEC IS THE ENGINEERING WORK</div>
        <p class="xp-learning-desc">The iterations where Claude produced working code on the first try were the ones with a fully defined spec: exact field names confirmed, exact date range set, exact output schema decided. Vague inputs produce vague code. The prompt work and the spec work are the real work. The code is just execution of decisions that were already made.</p>

<section class="xp-section">
  <div class="xp-heading-row">
    <h3 class="xp-heading">▸ DEV SECRETS DISCOVERED</h3>
    <div class="xp-subhead">development learnings</div>
  </div>
  <ul class="xp-learnings">
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">ASYNC APIS NEED POLLING, NOT WAITING</div>
        <p class="xp-learning-desc">Many analytics APIs queue requests and return a job ID rather than data immediately. The correct pattern: fire requests in a batch, wait once, poll all results together, write all results. Sequential fire-wait-fire-wait is the intuitive approach and the slow one. In this project, batching was 12 times faster. The same principle applies to any async API regardless of the platform.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">SCRIPTING ENVIRONMENTS HAVE HARD EXECUTION LIMITS</div>
        <p class="xp-learning-desc">Execution environments impose hard time ceilings per run. Any script handling a large date range will hit one. The solution is checkpointing: save progress after every unit of work, read it on the next run, resume exactly where you left off. Specifically in Apps Script, manually running a script from the browser stops when you close the tab. Only trigger-based executions run server-side and survive disconnects.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">DASHBOARD LABELS AND API FIELDS ARE DIFFERENT</div>
        <p class="xp-learning-desc">Every platform has a gap between what the UI shows and what the API accepts. In this case the dashboard displayed <code>Country = US</code> and the API required <code>geo_fields: [["United States"]]</code>. The only reliable way to find real field names is to read the API documentation. Guessing from UI labels produces code that compiles fine and returns nothing.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">ZEROS ARE DATA TOO</div>
        <p class="xp-learning-desc">When certain segments returned zero counts across all variants, the first instinct was a script bug. The actual cause was upstream: those users were not enrolled in the experiment at all, an issue with how the app tagged audience events. The script was correct. The input data was wrong. Knowing what a working result looks like is how you tell the difference between a pipeline failure and a data quality problem.</p>
      </div>
    </li>
  </ul>
</section>
