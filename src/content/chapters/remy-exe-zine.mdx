<Panel id="p-origin" num="01" title="LEVEL 1 START" open>

I needed a site to document all my AI projects. But I wasn't going to build a run-of-the-mill site. I needed something that oozes personality and my taste, where I could provide creative direction in collaboration with AI to create it.

This is the proof I can not only build functional stuff, but also awesome-looking design.

<PullQuote>
A site without a point of view is a CV in different fonts.
</PullQuote>

The framing landed quickly: a zine. Not a portfolio, not a blog, not a Notion page. A digital magazine, with me as editor, writer, designer, and developer. Issues come out at the cadence the work ships. Each chapter documents one project with the same template (LEVEL 1 START / BOSS FIGHT / INVENTORY / XP GAINED) and a different signature color. The whole site is one of the projects. This chapter is the one about how it got built.

</Panel>

<Panel id="p-fix" num="02" title="BOSS FIGHT">

Most websites get built around a content model. You decide what kinds of things go on the site (posts, projects, products), then design a layout that makes those things look right.

This one went the other way. The design language landed first. I wanted the site to feel like a videogame-flavored digital magazine. Pixel fonts where they could carry weight, a serif for body copy, a monospace terminal font for system messages. Signature colors per chapter, like a magazine using a different ink for each section. A pixel-art mascot, because of course.

The stack picked itself once the framing was clear.

Astro because the site is content-driven, not app-driven. Each chapter is a markdown document with components inline. Static output, fast loads, no client-side framework runtime to ship. The site is a magazine, not a SPA. Astro is the closest thing to "publishing platform that respects HTML."

Tailwind because the design system needed tokens (signature colors, type scale, spacing rhythm) and Tailwind is the cleanest way to lock those tokens at the config level and reuse them across components without writing CSS files for every variant. The static version of the site was a 60KB single HTML file with a 1,000-line <code>&lt;style&gt;</code> block. Migrating to Tailwind let the same design tokens live in one config file and propagate everywhere.

Other things considered: Next.js (overkill, app-shaped not content-shaped), plain HTML/CSS (the static version, fine until I needed to scale to multiple chapters), Eleventy (good fit, but Astro's component model felt closer to where I wanted the chapter templates to live).

<Gotcha tag="▸ GOTCHA">
Press Start 2P, the pixel-art font that does most of the loud typography on the site, doesn't have accented character glyphs. When the credits roll spelled my name as <code>RÉMY</code> in the pixel font, the <code>É</code> rendered as a smaller lowercase <code>é</code> from the browser's fallback font, sitting between an uppercase <code>R</code> and <code>MY</code>. It looked like the accent had been dropped in mid-render. The fix was to drop the accent in pixel-font contexts (the credits roll uses <code>REMY</code>) and keep it in body-text contexts where Fraunces handles diacritics fine. Real takeaway: pixel fonts encode the language they're designed for, usually English-only ASCII. Worth checking before falling in love with one.
</Gotcha>

<Gotcha tag="▸ GOTCHA">
The first four chapters were built one at a time, each with its full design system embedded in a <code>&lt;style&gt;</code> block at the top of the HTML file. By chapter five, the same 800 lines of CSS had been duplicated five times. Changing the cyan signature color now meant editing five files. Adding a new component meant five edits. The mistake wasn't writing it that way once. The mistake was not stopping at chapter two and pulling the shared rules into a single <code>shared/style.css</code>. The fix was a single extraction pass after all five chapters were homologated, when the design system was finally locked. Lesson: the cost of duplication grows linearly. The cost of extraction stays roughly flat. Extract early, even when "early" feels premature.
</Gotcha>

</Panel>

<div class="stack-section">
  <div class="stack-label">▸ CONTENT AND DESIGN SEPARATED</div>

  Every chapter's design lives in one shared stylesheet (<code>shared/style.css</code>). Every chapter's content lives in its own HTML file. Changing a color is a one-line edit in the stylesheet and every chapter, current and future, picks it up. Authoring a new chapter is a content task, not a styling task.

  This separation is the architecture. The marginal cost of adding a new chapter is the cost of writing its content. There's no system-rebuilding tax.

<div class="stack-section">
  <div class="stack-label">▸ EDITORIAL RULES</div>
  <ul class="personality-list">
    <li><b>No em-dashes.</b> Anywhere in body copy. Periods, commas, parentheses, semicolons instead. Em-dashes are a known AI-writing tell.</li>
    <li><b>First-person singular.</b> Everything written from "I." No "we," no "the team."</li>
    <li><b>Tab subtitles are fixed.</b> <em>the why</em> / <em>the fix</em> / <em>the stack</em> / <em>learnings</em>. Same in every chapter.</li>
    <li><b>Industry-then-project structure</b> in LEVEL 1 START when applicable. Industry framing first, then <code>▸ AT [PROJECT]</code> divider, then project-specific framing.</li>
    <li><b>Status tags.</b> <code>LIVE</code> for everything currently shipping. <code>WIP</code> for genuinely in-progress chapters that should be readable but flagged.</li>
  </ul>

<section class="xp-section">
  <div class="xp-heading-row">
    <h3 class="xp-heading">▸ AI POWER-UPS</h3>
    <div class="xp-subhead">building with ai</div>
  </div>
  <ul class="xp-learnings">
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">MOCKUPS BEFORE PROMPTS</div>
        <p class="xp-learning-desc">When building visual UI with AI, sketching the screen as text-only first (just labels and arrows on a page, no pixels) gets dramatically better results than describing it in prose. The AI can see the information architecture before it has to invent layout. Skip the IA step and the AI fills the gap with whatever generic SaaS pattern is statistically average.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">DESIGN LANGUAGE AS A BRIEF</div>
        <p class="xp-learning-desc">Loading the AI with the design tokens, font choices, signature colors, and editorial rules upfront means every component request lands in the same visual register. Without that, components drift toward whatever framework the AI saw most often. Front-load the brief, save hours of back-and-forth corrections.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">SHOW, DON'T TELL</div>
        <p class="xp-learning-desc">Pasting an existing component as a reference produces faster, more accurate variants than describing one from scratch. The AI is much better at "make this but for that case" than at "build me a card with these properties." Use the components you already have as the language.</p>
      </div>
    </li>
    <li class="xp-learning">
      <div class="xp-learning-body">
        <div class="xp-learning-title">AI WON'T VOLUNTEER ARCHITECTURE</div>
        <p class="xp-learning-desc">When you're shipping fast with AI, it ships fast with you. It will happily duplicate a 1,000-line stylesheet across five files if you ask it to build five files. It will not interrupt the flow to say "this is going to be painful in three months." That's the human's job. The lesson: at every milestone (second chapter, third feature, second similar component), pause and explicitly ask the AI to flag any structural decisions you're about to lock in by default. Otherwise you'll keep shipping and accumulate debt that only becomes visible when scale forces a refactor.</p>
      </div>
    </li>
  </ul>
